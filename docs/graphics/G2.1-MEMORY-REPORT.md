## 1. Executive Summary

This report delivers a comprehensive memory inspection of native ArenaOS executables across two integration milestones:
1. **Hardened Baseline (`sdl3_app`)**: Freestanding, SSE-free (-mno-sse), lightweight API-compatible implementation used for guest desktop qualification.
2. **Genuine Upstream SDL3 (`upstream_sdl3_demo`)**: Authentic upstream SDL 3.2.0 static archive integration linked against upstream `libSDL3_upstream.a`.

Both binaries were audited against the production kernel ELF validation constraints defined in `kernel/kernel/src/image_registry.rs`:
$$\text{MAX\_BYTES} = 262,144\text{ bytes } (256\text{ KiB})$$
$$\text{MAX\_LOAD\_PAGES} = 128\text{ pages } (524,288\text{ bytes})$$

## 2. Kernel Load Segment Evaluation Algorithm

The kernel validates registered dynamic images using `kernel/kernel/src/image_registry.rs`:
```rust
let mut pages = 0u64;
for seg in parsed.segs[..parsed.nsegs].iter() {
    let end = seg.vaddr + seg.memsz;
    let round = (end + 4095) & !4095;
    let span = round - seg.vaddr;
    pages += span / 4096;
}
if pages > MAX_LOAD_PAGES {
    return false; // dynamic Image exceeds load-page budget
}
```
Crucially, **only loadable `PT_LOAD` segments** count toward `MAX_LOAD_PAGES`. Dynamic VM allocations mapped at runtime via `SYS_VM_RESERVE` and `SYS_SHARED_MAP` (such as the window surface backing store) do **not** contribute to the executable's 128-page load budget.

## 4. Static `.bss` vs. Dynamic VM Heap Separation

A critical design requirement is separating static executable data from dynamically allocated memory:

```
+-------------------------------------------------------------+
|                     Virtual Memory Space                    |
+-------------------------------------------------------------+
| 0x000000 - 0x1ff000 : Unmapped Guard Space                  |
| 0x1ff000 - 0x200000 : Segment 0 (ELF Headers / Notes)       |
| 0x200000 - 0x21d0d4 : Segment 1 (.text code, 118,996 B)     |
| 0x21e000 - 0x226bd0 : Segment 2 (.rodata constants, 35,472) |
| 0x226bd0 - 0x22cf50 : Segment 2 (.eh_frame unwinding, 25,792)|
| 0x22d000 - 0x22d0e8 : Segment 3 (.data initialized globals) |
| 0x22d0e8 - 0x2603a0 : Segment 3 (.bss uninitialized memory) |
|   ├── s_stack:             65,536 B (64 KiB execution stack)|
|   ├── s_startup_snapshot:   4,096 B (ARST v2 gate buffer)   |
|   ├── s_heap_pool:        131,072 B (128 KiB memory arena)  |
|   └── SDL internal state:   8,888 B (Device / Window data)  |
+-------------------------------------------------------------+
| 0x261000 - 0x800000000000 : Dynamic Allocations (Not in ELF)|
|   ├── Granted Surface SHM: 768,000 B (Mapped via SYS_SHARED)|
|   └── Future C2 Heap:       16 MiB   (Mapped via SYS_VM_RES)|
+-------------------------------------------------------------+
```

### 4.1 Memory Allocation Analysis
1. **Stack**: Sized at 64 KiB, aligned to 4,096 bytes. Sits inside `.bss`. Handled by naked entry stub in `_start`.
2. **ARST Ingestion**: 4,096 bytes in `.bss`. Used during startup to safely snapshot Slot 0 before destroying the transport capability.
3. **Freestanding Allocator Scaffolding**: 128 KiB (32 pages). Sized to prevent exceeding `MAX_LOAD_PAGES`. In Milestone G2, an earlier 512 KiB heap segment failed dynamic image registration because 128 heap pages pushed total pages to 137. Trimming the heap to 128 KiB brought total pages to 61 (Baseline) and 100 (Upstream).
4. **Window Surface Backing Store**: Sized at 768,000 bytes ($320 \times 240 \times 4$ bytes plus frame headers). Allocated by `desktop` and mapped into the application process via `SYS_SHARED_MAP`. This memory is outside the ELF image and does not consume ELF load pages.
