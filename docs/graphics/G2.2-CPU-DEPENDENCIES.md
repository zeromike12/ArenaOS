## 1. Executive Summary

Milestone G2.1 and G2.2 successfully compiled authentic upstream SDL 3.2.0 source code into a static freestanding archive (`libSDL3_upstream.a`) and linked a native ArenaOS binary (`sdl3_upstream_demo`). 

However, **native ring-3 guest execution of the genuine upstream SDL3 binary is strictly blocked** by the current ArenaOS CPU architecture and kernel context-switch model. 

This document defines the exact hardware, ABI, and kernel dependencies required before genuine upstream SDL3 (and future applications such as Mesa softpipe, SuperTuxKart, or Blender) can execute safely inside the ArenaOS guest.

## 3. Root Cause Classification: Why Upstream SDL3 Emits SSE

The 2,036 `%xmm` instruction hits in `sdl3_upstream_demo` stem from three structural requirements of modern C code under the System V AMD64 ABI:

### 3.1 AMD64 System V Calling Convention (Hard Requirement)
The System V AMD64 ABI mandates that:
1. Floating-point arguments (`float`, `double`) are passed in `%xmm0` through `%xmm7`.
2. Floating-point return values are returned in `%xmm0` (scalar) and `%xmm1` (complex/pair).
3. In variadic functions (`printf`, `SDL_SetError`, `SDL_snprintf`, `SDL_LogEvent`), register `%al` must hold the number of SSE registers used (0 to 8). The function prologue must spill registers `%xmm0` through `%xmm7` into the register save area using `movaps` instructions (e.g. `movaps %xmm0, 0x50(%rsp)`).

Because upstream SDL 3.2.0 declares functions with `float` parameters (e.g. `SDL_SendMouseMotion(..., float x, float y)` and `SDL_GetWindowSurface`), the compiler **cannot emit AMD64 System V code without SSE registers unless a non-standard soft-float ABI is used across the entire toolchain**.

## 4. Current ArenaOS Kernel CPU State & Hazards

A comprehensive audit of the ArenaOS kernel (`kernel/kernel/src/arch/x86_64/`) established two distinct hazards:

### 4.1 Hazard 1: Immediate `#UD` (Invalid Opcode Fault)
- **Mechanism:** In `kernel/boot/src/m1.rs` and `kernel/kernel/src/arch/x86_64/`, control register `CR4` is initialized with physical address extensions and page global flags, but **`CR4.OSFXSR` (bit 9, 0x200) is NEVER set**.
- **Hardware Rule:** When `CR4.OSFXSR == 0`, any execution of an SSE/SSE2 instruction (`movss`, `movaps`, `xorps`, `comiss`, etc.) in user space (CPL 3) triggers CPU Exception Vector 0x06 (`#UD Invalid Opcode`).
- **Kernel Response:** `kernel/kernel/src/arch/x86_64/idt.rs` traps vector 0x06 and executes:
  ```rust
  fn ud_handler(...) {
      exit_on_user_fault(6);
  }
  ```
  The process is unconditionally killed immediately upon hitting its first SSE instruction.

### 4.2 Hazard 2: Cross-Thread State Corruption
- **Mechanism:** In `kernel/kernel/src/arch/x86_64/context.rs`, the thread context-switch implementation (`switch_context` and `new_thread_stack`) saves only integer general-purpose registers:
  $$\text{Frame: } [\text{RFLAGS}, \text{R15}, \text{R14}, \text{R13}, \text{R12}, \text{RSI}, \text{RDI}, \text{RBP}, \text{RBX}]$$
- **Hazard:** The kernel does not execute `fxsave`/`fxrstor` or `xsave`/`xrstor`. Even if `#UD` were bypassed or if code executed legacy x87 instructions (which do not trigger `#UD` because `CR0.EM` is not set), **the CPU's FPU and vector registers are shared across all threads without preservation**.
- **Consequence:** Preemptive multitasking or thread yielding silently corrupts floating-point and vector register state across threads.

## 5. Architectural Requirements for Luna / Core OS

To enable authentic upstream SDL3 execution without modifying upstream source code, the following architectural facilities must be implemented by the CPU state management track:

### 5.1 CPU Initialization (`kernel/boot` & `kernel/arch`)
1. **Enable FXSAVE/FXRSTOR in CR4:**
   ```rust
   // Set CR4.OSFXSR (bit 9) and CR4.OSXMMEXCPT (bit 10)
   let cr4 = read_cr4();
   write_cr4(cr4 | (1 << 9) | (1 << 10));
   ```
2. **Clear Emulation in CR0:**
   ```rust
   // Clear CR0.EM (bit 2); ensure CR0.MP (bit 1) and CR0.NE (bit 5) are set
   let cr0 = read_cr0();
   write_cr0((cr0 & !(1 << 2)) | (1 << 1) | (1 << 5));
   ```

### 5.2 Thread FPU Context Management (`kernel/sched`)
1. **Thread State Buffer:** Allocate a 512-byte, 16-byte-aligned FPU save area (`fxsave_area`) inside each thread descriptor or allocated alongside the thread stack.
2. **Context Switching:**
   - On switch out: execute `fxsave64 [thread.fpu_area]`.
   - On switch in: execute `fxrstor64 [thread.fpu_area]`.
   - Alternatively: implement lazy switching via `CR0.TS` and the `#NM` (Device Not Available, vector 7) exception handler.
3. **Thread State Initialization:** On thread creation (`new_thread_stack`), initialize the FPU save area with `fninit` and standard `MXCSR` defaults (`0x1F80`, masking all SIMD floating-point exceptions).

## 6. Graphics Subsystem G2.2 Stance & Policy

1. **No Compromise Policy:** We will **not** hack upstream SDL3 core files with custom integer approximations or weaken SDL3's semantics merely to force a demonstration before the kernel supports CPU floating-point state.
2. **Honest Qualification:** The genuine upstream target (`sdl3_upstream_demo`) remains statically verified and tested for build provenance, but is honestly classified as **EXECUTION BLOCKED on CPU State (Blocker B-FP-2)** until Luna delivers Phase 14 / CPU state support.
3. **Compatibility Baseline Maintained:** The hardened baseline (`sdl3_app`) strictly avoids SSE registers and will continue to serve as the live guest qualification vehicle for windowing, presentation, and input.
