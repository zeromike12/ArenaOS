## 3. Working Integrations (G2.2 Completed)

### 3.1 Canonical ARST v2 Ingestion
Arena 1 has eliminated partial startup checks and replaced them with Arena 2's canonical ARST v2 startup gate:
- Slot 0 is verified as a `SharedRegion` with rights `READ | DESTROY` and exactly 1 page.
- The 4096-byte ARST v2 page is mapped, copied into a private static `.bss` buffer, unmapped, and Slot 0 is destroyed immediately.
- Canonical layout rules (magic `ARST`, version 2, header bytes 128, contiguous section offsets, zero padding) are strictly enforced before any application code executes.
- If validation fails, the process exits immediately with exit code **122** (matching C2 convention).

### 3.2 Live Capability Inventory Verification
Arena 1 now executes the full 128-slot capability inventory check:
- Slots 1 through `capc` must be occupied with descriptors matching the recorded kind and rights.
- Slots `capc + 1` through 127 must be unoccupied.
- Any unexpected grant or missing capability fails closed with exit code 122.

### 3.3 Allocator Safety Hardening
In accordance with C2 requirements, Arena 1 refactored `arenaos_memory.c`:
- Allocation headers are 32 bytes (16-byte aligned), ensuring that returned pointers are strictly 16-byte aligned across all allocation sizes.
- Added ownership validation: magic tag verification (`0x4152454E414D454DULL`), heap boundary bounds checking, alignment checks, and double-free protection.
- Safe `realloc`: unvalidated or foreign pointers are refused without mutating heap state; allocation failures preserve the original block.

## 4. Architectural Resolution for Blocker B-GFX-1

### 4.1 The Problem
In `docs/compat/C2-FINAL-REPORT.md`, Arena 2 documented **Blocker B-GFX-1**:
> "A graphical app receives BadgedEndpoint, SharedRegion, and Notification descriptors, all with role `Other` (0). Nothing in the record says which SharedRegion is the surface, or which endpoint is the compositor. Choosing by slot number is an ABI assumption."

### 4.2 Proposed Solutions
To enable a single unified startup gate across both console and graphical applications, three options exist:

1. **Option A: Explicit Role Allocation (Recommended for ADR Review)**:
   Extend ARST v2 role enumeration in userspace and desktop:
   - `ROLE_GRAPHICS_ENDPOINT = 9` (BadgedEndpoint, rights `WRITE`)
   - `ROLE_GRAPHICS_SURFACE = 10` (SharedRegion, rights `READ | WRITE`)
   - `ROLE_GRAPHICS_NOTIFY = 11` (Notification, rights `WRITE`)
   *Advantage:* Pure contract-based discovery without positional assumptions.

2. **Option B: Protocol-Level Handshake (Immediate Graphics Fallback)**:
   A graphical application receives a single BadgedEndpoint. The client performs an `ADSK_OP_CONNECT` exchange over IPC, and Desktop dynamically transfers the window's `SharedRegion` surface and pacing `Notification` capabilities across the IPC call.
   *Advantage:* Requires no changes to frozen ARST v2 descriptor tables.

3. **Option C: Documented Graphical Launcher Profile**:
   Preserve the current Phase 13 convention as a frozen graphical contract:
   - Slot 1: Desktop Service BadgedEndpoint
   - Slot 2: Window Surface SharedRegion
   - Slot 3: Notification (Timer signaling)

Arena 1 has standardized on Option C for existing G2.x releases while supporting Option A for future ADR review.
