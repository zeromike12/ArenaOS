# C2.1 handoff: B-GFX-1 (graphical service identity) and notification selection

Status: **PROPOSAL, documentation only.** No ABI, wire, or capability change is made here.
Nothing in this document accepts an ADR. Decisions belong to architecture review and to
Arena 1 (desktop and graphics owners). Branch: `arena/f89ea987-arenaos`.

Evidence labels: **host** (ASan+UBSan host test), **static** (build or audit), **guest**
(exact-PASS QEMU run), **blocked** (cannot be done under the current contract).

## 1. The problem, restated

Startup ABI v2 (ARST) gives a graphical application BadgedEndpoint, SharedRegion, and
Notification descriptors. All of them carry role **Other** (5). The record does not say
which SharedRegion is the window surface, or which BadgedEndpoint is the compositor. Two
descriptors of the same kind and rights are indistinguishable by contract.

The runtime must not choose by slot number, by position, or by a guess. The task forbids
it, and it is not safe.

## 2. What C2.1 changed for notifications (implemented, host-tested)

This is the part of B-GFX-1 that C2.1 could fix without an ABI change.

- Stream-wait notification selection moved into the pure function
  `arena_startup_pick_notification(caps, count)` (`src/startup_query.c`).
- A candidate is a descriptor with role **Other**, kind **Notification (3)**, and rights
  exactly **READ|WRITE**.
- Exactly one candidate returns its index. **Zero, two or more, or a NULL table returns
  `ARENA_ARST_NONE`.** Ambiguity is refused, not resolved.
- With NONE, a blocking stream wait returns `ARENA_E_NO_WAITER` (`src/streams.c`,
  `wait_for_peer`). It never binds to another notification.
- Host tests (`host/test_libc.c`, `test_notification_selection`) cover: headless (no table
  and empty table), missing, one valid, two equal, read-only, wrong kind (BadgedEndpoint
  with RW), wrong role (StreamWake), malformed (kind 0, zero rights), a graphical mix with
  one notification, and a graphical mix with two notifications.
- Result: **host** only. `B-NTF-1` (`C2-FINAL-REPORT.md`) is closed for the runtime. The
  production side may still give an app two notifications; the app then gets no stream
  waiter. That is a refusal, not a misbinding.

Not changed: ARST v2 (no new role, no flag, no wire change). `tools/startup_abi.py` is
unchanged.

## 3. What is still blocked: identifying the surface and the compositor

Three ways to give a graphical app an unambiguous identity, compared. None is chosen here.

### Option 1: validated, versioned launch convention

The installed application's signed manifest (APB1) declares the expected graphical
descriptor layout under a version string, for example `graphics.v1: surface=<index>,
endpoint=<index>`. The launcher checks the actual record against the declaration and
refuses on any mismatch. The app then reads the indices it was promised.

- No ARST wire change. The check happens in the launcher, not in the C runtime.
- Depends on the manifest format and its signed-package handling. **The task forbids changes
  to signed-package verification,** so this needs its own authorization, and the manifest
  field would be a new public format.
- Still positional: the index is trusted only because the launcher checked the record it
  built. Any launcher that skips the check reintroduces the guess.

### Option 2: protocol-level identification (no ABI change)

After launch, the app identifies its surface over the BadgedEndpoint with a request whose
reply names the surface. The endpoint badge identifies the app session. The desktop answers
only if it has exactly one surface for that session, and refuses otherwise. The reply is
the authority: the app keeps only what the desktop named.

- No ARST change, no new role, no new capability kind. The protocol is Arena 1's to define
  under its own specification. C2 does not define it.
- Requires a round trip before the surface is usable. The desktop must hold per-session
  state. That is already the pattern of the desktop's badged application sessions
  (ADR-0090), so the cost is a new message, not a new mechanism.
- Trust is in the desktop's reply, which the desktop must make unambiguous. This matches
  how the desktop already names windows to applications.

### Option 3: future Startup ABI extension

Add a service tag per descriptor (for example a `u16` service identifier), or a new role
such as `GraphicsSurface`. The launcher fills it from the manifest, and the runtime matches
on it. This is the only option that makes the record self-describing at launch.

- A wire change: needs an ADR, a version bump, and coordinated changes in the Rust startup
  crate (`userspace/arena-startup-abi`, `userspace/arena-platform/src/startup.rs`), the Python
  tool (`tools/startup_abi.py`), and the C runtime (`src/startup.c`). The task forbids this
  for C2.1. It is recorded as a proposal only.
- Also needs M9 resolved first: `tools/startup_abi.py` has `CAP_MAX = 4`, so the Python
  side cannot even encode the seven-descriptor record the Rust side allows.

## 4. Comparison

| | Option 1 launch convention | Option 2 protocol identification | Option 3 ARST extension |
|---|---|---|---|
| ABI or wire change | none in ARST; new manifest field | none | yes (ARST version, ADR) |
| Signed-package handling | touches manifest format (needs authorization) | none | none directly |
| Unambiguous at launch | yes, if the launcher checks | no, after one round trip | yes |
| Owner | launcher and packaging | Arena 1 desktop protocol | architecture, Rust and C |
| Works with today's runtime | needs a launcher change | needs the app's protocol code | needs everything above |
| Risk | positional trust if a launcher skips the check | desktop must refuse ambiguity | largest change |

## 5. Recommendation (for review, not decided)

1. **Near term, no ABI change: Option 2.** Arena 1 defines the identification message on the
   BadgedEndpoint; the desktop answers only when unambiguous; the app uses only the reply.
   This unblocks a graphical smoke test without a privileged path or a guess.
2. **Launch-time check: Option 1, as an added safety net,** if packaging is authorized to
   carry a versioned layout. It does not replace Option 2.
3. **Option 3 only if a real need appears** (for example several same-kind graphical
   descriptors that must be told apart before the first message). It needs an ADR and
   architecture review first, and M9 must be fixed beforehand.

What C2.1 does not decide: which option is adopted, the message format for Option 2, and any
manifest field for Option 1.

## 6. Current graphical contract (what Arena 1 can rely on today)

- `arena_startup_count_kind(kind, rights)` counts descriptors by kind: host-tested. It can
  tell that a surface exists; it cannot tell which one.
- `arena_startup_pick_notification` is the only selection the runtime makes, and it refuses
  ambiguity (section 2).
- **No graphical guest run exists.** The optional smoke test was not attempted (C2 final
  report). Status: **blocked** for service identification, **host** for the count and
  notification selection.

## 7. Open items for architecture and Arena 1

- Choose Option 2 (or record why not) and name the owner of the identification message.
- Decide whether a manifest layout field (Option 1) is in scope for packaging.
- Record the decision as an ADR before any ARST change (Option 3).
- Arena 1 must not index graphical descriptors by slot number. Use kind and rights, refuse
  on ambiguity, and do not assume the order of the record.
