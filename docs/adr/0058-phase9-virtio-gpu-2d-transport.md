# ADR-0058 — Phase-9 virtio-gpu 2D device service transport

Status: **Proposed transport design; standalone wire codec only, no GPU service or qualification claimed**
Date: 2026-10-01

## Resource and authority budget

ADR-0056's GOP fallback is an exclusive `Mmio/READ|WRITE` granted to a ring-3 display server. The current four display grants are GOP MMIO, serve endpoint, MemoryPool/WRITE and SharedDma/READ. If the boot PCI scan finds virtio device type 16, an additional **fifth** explicitly bounded `Mmio/READ|WRITE` grant for that function's non-I/O virtio capability BAR fits `MAX_INHERIT=5`. No blanket PCI mapping, raw-physical syscall, extra capability slots or Notification slot is justified. The GPU controlq can be completion-polled with an HPET-bounded deadline and scheduler yield; a relay Notification would exceed this particular grant budget. The *current* shared virtio core's `discover` requires MSI-X even at a zero vector minimum and `queue_setup` always calls `SYS_IRQ_RELAY`, so it cannot simply be reused unchanged for this path. Add a separately audited **generic polling queue setup** with MSI-X vector `0xffff` (disabled), bounded ring offsets/doorbell and no relay syscall; admit a `min_msix=0` discovery only for callers deliberately selecting this path. Preserve every historical driver's nonzero-vector relay behavior byte-for-byte and prove both the new polling path and old interrupt path. Do not treat a BAR's numeric address as authority: only the held fifth device cap maps it. Validate the BAR length, device type, vendor ID and the shared virtio PCI capabilities against the kernel-recorded function before granting. The older `virtio_for_caller` device-info gate checked an MMIO cap's physical *base* but not that its page count covered every common/notify/ISR/device capability range. The hardened gate now checks presence, same BAR, minimum lengths, offset+length against the recorded BAR, actual held-cap page coverage, and READ for information versus WRITE for relay. A real ring-3 short-lived probe receives a *one-page*, READ-only block BAR prefix while its device's notify structure is in page four: `SYS_DEV_INFO` must refuse without changing the output; omission of only the production cap-extent check makes the guest halt and byte-exact restored EFI boots with QMP pixels. The parser's own host tests cover overflowed capability layouts. This is refusal-only hardening of existing authority, not broader driver access. `SYS_DEV_INFO` has a frozen 12-word ABI, so do not silently append BAR size or reinterpret reserved words. The polling helper's `cfg_len`/`notify_len` must come from that checked gate, never merely from attacker-controlled arithmetic. A GPU-only boot still starts a service without manufacturing a GOP cap; grant indexes must be explicit for both configurations and tested, never guessed from the number of caps. A headless/no-GPU machine remains headless without a painted marker.

Displayd owns all queue descriptor memory and device-visible scanout backing in generic SharedRegions. Only the separately held SharedDma/READ authorizes the possession-gated physical backing query after validating the region cap and its bounds. The compositor may receive an attenuated scanout mapping but no GPU BAR, DMA bearer or physical address. Audit the total eight-region / 2048-page live limit: one ≤512-page scanout and a bounded queue/command allocation must leave room for client surfaces. Explicit boot grants keep the historical shell, manager and package worker device-cap-free.

## Negotiation and wire

Follow OASIS virtio v1.3 §5.7, version-1 PCI transport and the existing ArenaOS userspace virtio core: reset, acknowledge/driver status, negotiate VERSION_1, reject unrecognized mandatory bits, choose one controlq, preflight queue descriptors/buffer lengths and announce DRIVER_OK only after validation. The Phase-9 path is strictly 2D; negotiate no virgl/3D features. GET_DISPLAY_INFO must return a success response with a live scanout, 32-bit dimensions within the same checked ≤2 MiB buffer bound and a supported color layout; a returned display ID, resource ID or host framebuffer address cannot authorize anything. Reserve one resource ID with a monotonic local generation. CREATE_2D(XRGB8888/BGRX-compatible), ATTACH_BACKING (checked backing length), SET_SCANOUT, TRANSFER_TO_HOST_2D and RESOURCE_FLUSH are the only ordinary rendering command chain. Response type, response used-length, echoed fence (if negotiated), bounded rectangle/offset and a wall-clock completion deadline are validated for **every** command; a completion that is short, unexpected or late fails closed, not a synthetic success. On controlled teardown: SET_SCANOUT to zero, DETACH_BACKING and UNREF, checking the same response discipline. Never pass an arbitrary client physical number into an attach descriptor.

Prefer GPU only when the actual command handshake and display-info succeed. If initialization fails before accepting clients, use the real GOP fallback only if its cap and handoff geometry are valid; otherwise explicitly report headless/refusal. Once an active transport fails, refuse presents and drain/retire its outstanding command state. Do not switch transport mid-frame or advertise a restart without proven resource/endpoint semantics. GPU and GOP must use the same typed display MODE/PRESENT protocol, with displayd alone performing checked transfers/flushes or volatile MMIO copies.

## Partial implementation ledger

`userspace/gpu2d` is an independent, allocation-free `no_std` 2D wire encoder/response parser with fixed command lengths, checked geometry/backing/refusal, plus a one-outstanding polling queue helper over explicit guest-owned DMA/MMIO memory. Eight host tests including strict parsing of the frozen `SYS_DEV_INFO` record, mocked MMIO/used-ring corruption and short-response fuzz, fmt/clippy and bare-metal build pass. A host RED control deliberately omits the production response-opcode check, requires an exact ACK mismatch test to fail, restores byte-identical source and proves GREEN. This remains host-only; it cannot substitute for a guest GPU completion or QMP screenshot. The helper is **not linked to displayd** and does not interact with a real device, cap gate, graphics endpoint or QEMU GPU display. Keep its result separate from every guest claim below.

## Evidence, not assumptions

Boot QEMU with `-vga none -device virtio-gpu-pci` and real QMP screendump; assert expected pixels after CREATE→ATTACH→SCANOUT→TRANSFER→FLUSH and inject an input event independently if compositor input is ready. Boot with `-vga std` and no GPU for the existing GOP oracle, and with no GPU/no VGA for clean headless refusal. Force a GPU-handshake rejection to test *genuine* GOP fallback, plus unexpected response, missing DMA cap, malformed backing/span, queue exhaustion and teardown/last-ref controls. Correlate guest resource peaks and PCI command counters with QMP pixels, not serial-only claims. Do not mark GPU present in tests or docs until this actual service and its negative controls pass.
