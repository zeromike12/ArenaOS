# ADR-0056 — Phase 9 bounded graphics, shared-region authority and visual proof

Status: **Accepted design for Phase 9; implementation and guest qualification pending**
Date: 2026-10-01

## Substrate audit and decision

The qualified Phase-8.5 baseline (`0c969d1`) has 32 capability slots/process, at most five inherited grants, 16 user-region entries/thread, 32 process records, 10/10 boot-created endpoints, 18/18 Notifications, physically contiguous frame allocation, one-page owned `Untyped` caps, descriptive `Memory` and `Mmio` caps, and single-page owned self-maps. `Memory` does *not* own RAM: user-minting one from a physical number would bypass ownership and teardown. Lending `Untyped` prevents mapping, correctly; consuming an owned `Untyped` transfers a **single page** to the address space. A 640×480×4 scanout is 1,228,800 bytes (300 pages). It cannot be represented as hundreds of cap slots or registered user regions. Existing mechanisms do not safely express a useful shared surface. Thus one generic, finite shared-memory primitive is necessary; no graphics/window semantics enter the kernel.

**Boot-image namespace collision:** the existing embedded Image IDs 0..26 are all occupied and ADR-0055 fixes dynamic FIRST=27 with successful IDs allowed through `u32::MAX`. New static graphics services cannot take ID 27 (or a reserved high ID) without breaking dynamic monotonicity/stale-ref tests. Do not shift FIRST, invent a private registrar, or weaken the one-unretired-dynamic-child rule. Add a separate kernel-minted `BootImage { index }` capability kind for new fixed embedded services, held by the manager with READ|COPY for supervised spawn and handed only by explicit boot grants. Existing `Image { img_id:0..26 or >=27 }` semantics, describe results and dynamic registration remain byte-for-byte unchanged. `SYS_SPAWN` admits either existing Image or the new BootImage kind by possession and READ; the BootImage path uses the unchanged ELF validator/loader, is **not** tagged dynamic and never delegates device caps implicitly. Its own upper bound (at most four new embedded services) and right attenuation are independently tested; it does not turn a signed staged package into a boot image. This separates two already-existing provenance classes without creating a new signer, policy oracle or general load-by-name operation. The UEFI handoff currently contains only memory regions, image layout and ResetSystem, not GOP. The x86 kernel has no display driver. The shared userspace virtio 1.0 PCI core handles discovery, BAR, split queues and interrupt relay; virtio-gpu is not yet discovered. Production inputd owns the virtio-input keyboard and injects decoded keys into the console; the existing endpoint READ mode is only a test, so graphics input must be a second explicitly attenuated delivery route without disrupting the console. Boot's firmware bindings have HandleProtocol and the final memory map; GOP information is captured **before** ExitBootServices and copied as plain data. No framebuffer pointer or UEFI protocol methods survive in a client or kernel GUI policy.

## Generic SharedRegion ABI (not a graphics object)

Add an independent `SharedRegion` cap kind and kernel-minted `MemoryPool/WRITE` allocation authority (only the manager and the expressly delegated display/compositor hold it); a separate `SharedDma/READ` bearer, held only by the display service, authorizes gated physical backing queries. Numeric IDs and a phys argument are never allocation or DMA authority. Use a monotonically increasing full-generation ID, fixed registry of at most **8** simultaneously live objects, each **1..=512 pages** (at most 2 MiB), and total live allocation at most **2048 pages** (8 MiB). Allocate a contiguous run using the existing frame allocator only *after* preflighting destination cap slot, size, per-object and aggregate budgets and registry ID exhaustion. On any allocator failure, return BUSY without changing the published registry/cap/ID; zero every page before publishing (no cross-client information leak). Reject unsigned overflow and noncanonical flags. The creator gets READ|WRITE|COPY|DESTROY; copies/IPC transfers can only attenuate. `SYS_SHARED_CREATE` and `SYS_SHARED_MAP` are additive syscall numbers after 34, with explicitly zero reserved args, typed BAD_ARG/BAD_ADDRESS/BUSY and no pid-name authorization. MAP is **self only**, requires READ for read-only and WRITE for RW, always NX, rejects region-table/VA conflicts and refuses before publishing a partial map. Kernel chooses VA (one registered span); user gets no raw physical address from a numeric ID. Only the device service with an *independently granted* DMA/right obtains a bounded physical backing description for the region; ordinary clients may not invoke generic `SYS_CAP_PHYS` on this kind. No copy can amplify.

Registry holds the frames until the last cap, mapping and in-flight IPC escrow reference is gone; dropping a cap never frees a still-mapped region. A mapping pins its object even when all caps are revoked. Process death removes every mapping pin and cap, and neither ordinary page-table teardown nor last-cap teardown may free a shared page twice. Physical run is freed once the final pin/reference is gone. Kernel performs a stable-boundary independent capspace/IPC/mapping conservation walk, tests missing-credit RED and restored GREEN, and refuses generation/stale-ID reuse. Mapping/buffer rights are object capabilities, not numeric token rights. No CAP_SLOTS increase.

## Display authority and device paths

The boot stage looks up GOP, validates supported 32-bit direct color layout, mode geometry/stride/byte span and framebuffer physical bounds, and records only the bounded tuple in handoff; if unsupported, records unavailable. The kernel mints a **single device MMIO cap** to the display server, never to compositor or clients. Framebuffer mapping is UC, NX, checked against handoff and never allocator-owned. The kernel never draws pixels, interprets GPU commands or composites. GOP fallback is actual writes through that mapped window, with an explicit typed MODE/PRESENT v1 display endpoint; no fabricated virtio-gpu claim when absent.

When virtio-gpu (device type 16) is present, display service alone receives its BAR and bounded control queue. Implement OASIS Virtio v1.3 §5.7 2D only: negotiated VERSION_1, GET_DISPLAY_INFO, CREATE_2D, ATTACH_BACKING, SET_SCANOUT, TRANSFER_TO_HOST_2D, RESOURCE_FLUSH, DETACH_BACKING and UNREF; check each completion type and byte length, time out or fail closed, never 3D/virgl. Prefer GPU when it actually passes handshake/display-info; fall back to GOP if device absent or initialization fails *and valid GOP remains*. Format fixed to 32-bit XRGB/BGR-compatible v1, one scanout, tested width/height/pitch. Display owns the device and a scanout backing region; compositor may write the scanout's shared pixels via an attenuated cap but cannot map the physical GOP window or GPU BAR. Display alone receives a separate DMA designation; a client-supplied physical number is never trusted. PRESENT validates checked rectangle and actual object identity/rights before flushing or copying. Bound queue depth and pending presents; release device resource/region on orderly teardown. Fatal display death makes compositor fail closed, not silently regain hardware authority by name.

## Compositor, input, text and toolkit

The compositor holds a separate display PRESENT endpoint and an attenuated shared scanout cap; clients receive only the compositor client endpoint plus per-surface bounded SharedRegion caps. It owns at most **4 clients / 6 surfaces** with max surface 320×200×4, only opaque XRGB. Each surface has a monotonic generation identity, owner bearer tied to the client's endpoint/cap possession, width, height, position, z-order and state; slot number and sender pid alone do not authorize operation. Create, move, damage/present, focus and destroy v1 operations are typed, finite and receiver-checked. All arithmetic uses checked multiplication/addition; rectangles clipped against surface then screen. The compositor composes a deterministic background + visible surfaces in z-order, never grants framebuffer/GPU/MMIO. On child death it drops all that client's surfaces and focus before slot reuse; stale IDs cannot revive authority. Invalid IPC-landed caps are disposed even on refusal. Additional endpoints (display, compositor and an attenuated input feed) require a **documented fixed increase from 10 to 13**, with 13/13 and mutation-free fourteenth refusal measured; do not increase Notifications or inheritance ceiling merely for convenience.

Inputd continues pushing the exact historic decoded keyboard bytes to the serial-compatible console path. For graphics it sends independently typed events from its real virtio-input queue through a private compositor route; only a manager-granted receiver cap permits that route. The compositor alone selects focus; one focused client's event queue receives typed key events, other clients none. Explicit focus change and death clear state. If the existing input device reliably exposes pointer/tablet events with bounded extra queue semantics, support and QMP-inject it; otherwise do **not** claim pointer support or fabricate events. Cap focus/input queue at 16; overflow refuses/drops with explicit counter, no overwrite.

Use an ArenaOS-owned fixed 8×8 bitmap ASCII font with a documented glyph table and deterministic replacement glyph; no runtime parser or third-party font crate. Bound glyph lookup, render and clipping, and test known glyph pixels. Ship a separate static no_std toolkit with pixel canvas, fill/rect/text, surface create/present and input event APIs. Run two independent clients with distinct caps and overlapping surfaces; a small independently signed dynamic client is optional only if Phase-8.5 single-unretired-child bound, 4096-byte signed v1 wire and existing manager lifecycle permit it without weakening old guarantees. No desktop chrome, launcher or Phase-10 programs.

## Qualification and refusal criteria

Capture real QEMU pixels (QMP screendump or equivalent), assert geometry, color at display-pattern/background, overlap, clipping, known glyph, toolkit element, removal and focus change coordinates. Inject real key via QMP, verify only focused client changes pixels/state, keep serial shell alive. Include deliberate composition/glyph RED mutation and restored GREEN. Exercise wrong/missing/attenuated caps, stale IDs, overflow, table/buffer full, process death, optional GPU/GOP fallback, resource before/after repeated cycles and independent reference accounting. All earlier 60 historical suites must remain. After last code change require full suite, final-image-bound fresh 100/100 that actually exercises graphics readiness/pixels, and independently extracted hashed archive boot with its own graphical capture.

**Limitations:** one scanout, software 2D, fixed font and opaque surfaces; no GUI security against malicious **compositor** or device-service compromise (they are graphics TCB), no anti-rollback promise, no Phase-10 desktop. A missing device yields explicit fallback/refusal, not a false PASS.

Specification references: [OASIS Virtio v1.3 §5.7](https://docs.oasis-open.org/virtio/virtio/v1.3/csd01/virtio-v1.3-csd01.html), UEFI 2.10 Graphics Output Protocol §12.9. This ADR freezes bounds and authority before dependent implementation; any observed mismatch requires correcting design and tests before claiming completion.
